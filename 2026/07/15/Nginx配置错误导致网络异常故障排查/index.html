二、抓包分析

查看 Response Header：

可以发现：

  • 请求已经到达 Nginx
  • 返回的是 HTTP 500
  • 并没有 Access-Control-Allow-Origin (因为一个响应头中不能出现两次Access-Control-Allow-Origin，因为已经在后端添加了，因此在nginx中重复配置，所以这个不是问题)

因此：

浏览器提示 CORS，只是因为 500 响应没有携带 Access-Control-Allow-Origin，真正的问题还是 HTTP 500。
而且Content-Type: text/html，而非：Content-Type: application/json，说明500是nginx返回的，不是后端程序返回的。

此时可以排除：

  • DNS 解析失败
  • SSL 握手失败
  • 网络不通

三、查看 Spring Boot 日志

Spring Boot 日志中发现了一些异常，例如：java.lang.NullPointerException，以及：ServiceException: 产品查询为空
但是这些异常全部发生在：queue-2线程中，例如：MeituanAriConsumer，属于 Redis MQ 消费线程。

浏览器访问的是：GET /admin-api/hotel/room/getRoomAll
对应的 Spring MVC 请求线程应该是：http-nio-48080-exec-*
因此这些 Redis 消费异常虽然需要处理，但并不是导致 HTTP 500 的直接原因。

九、排查经验总结

很多时候浏览器提示：CORS Error，真正的问题并不是 CORS。

推荐排查顺序：

不要因为浏览器提示：No Access-Control-Allow-Origin就一直修改跨域配置。

真正值得关注的是：HTTP 500，只有找到导致 500 的根因，问题才能彻底解决。

十、总结

本次故障形成了一条完整的故障链：

排查结论

现象 原因 是否根因
浏览器提示 CORS 500 响应未返回 Access-Control-Allow-Origin ❌
Axios Network Error 浏览器因跨域策略屏蔽了 500 响应 ❌
HTTP 500 Nginx 无法建立新的 upstream 连接 ⚠️
worker_connections are not enough Nginx Worker 连接耗尽 ⚠️
Spring Boot 请求耗时过长 / 后端连接长期占用 导致 Nginx 连接无法及时释放 ✅（最终需要继续排查）

经验总结

浏览器提示的错误往往只是表象。

本次故障中：

  • CORS 不是根因；
  • DNS 也没有任何问题；
  • worker_connections 不足只是触发了 500；
  • 真正值得继续排查的是 为什么 Spring Boot 与数据库、Redis 等后端资源响应变慢，导致 Nginx 连接长期占用。

对于这类问题，建议优先从 HTTP 状态码 → Nginx 日志 → 应用日志 → 数据库 的顺序进行定位，而不是一开始就怀疑跨域配置。
